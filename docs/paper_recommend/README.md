# 論文レコメンド自動化 — 運用ドキュメント

週次で arXiv を探索し、選定結果を Notion の論文DBへ自動登録する仕組みの運用手順書。

---

## 全体像

```
Routine（サーバー側スケジューラ）
  └─ 毎週日曜 06:50 JST に新しいセッションを起動
       └─ このリポジトリを clone
            └─ docs/paper_recommend/<track>_prompt.md を読む
                 └─ 「## 現行版」のコードブロック全文を指示として実行
                      ├─ 出力1: チャット（セッションに残る）
                      ├─ 出力2: Notion DB へ登録
                      └─ 実行記録を <track>_prompt.md に追記して commit & push
                 └─ 完了時にプッシュ通知
```

**プロンプト定義ファイルが唯一の正（single source of truth）。**
Routine 本体には「そのファイルを読んで実行しろ」という短い起動文しか入っていない。
したがってプロンプトの改訂は、このリポジトリのファイルを編集して `main` に反映するだけでよく、
Routine を触る必要はない。変更履歴は git で追える。

## 登録済み Routine

> **現在すべて無効化（`enabled=false`）。** API 経由で作った Routine には Notion コネクタが
> 付かず、発火しても Notion 登録が落ちることを実測で確認したため。
> claude.ai の Routines 画面で作り直すこと（手順と貼り付け用の起動文は `routine_prompts.md`）。
> 作り直したら下の Trigger は削除してよい。

| トラック | Trigger ID | cron (UTC) | 実行時刻 (JST) | 基準期間 | プロンプト定義 | Notion DB |

全トラック共通で通知はプッシュのみ（メールなし）。

### UTC と JST の曜日ずれ（重要）

cron は **UTC** で評価される。JST は UTC+9 なので、朝 06:50 JST は前日 21:50 UTC になり、
**曜日フィールドが1日前にずれる**。上の表の cron が意図した曜日と一致しないように見えるのはこのため。

| 実行したい JST | cron (UTC) | 曜日フィールドの意味 |
|---|---|---|
| 日曜 06:50 | `50 21 * * 6` | 土曜 |
| 水曜 06:50 | `50 21 * * 2` | 火曜 |
| 土曜 06:50 | `50 21 * * 5` | 金曜 |

同じ理由で、**起動セッションの `date` は狙った曜日の前日を返す**。
金融トラックの仕様書は対象期間を実行曜日で分岐させている（水曜なら月・火、土曜なら水・木・金）ため、
ここを取り違えると対象期間がまるごとずれる。各 Routine の起動文の冒頭で
「この実行は JST の◯曜朝であり、`date` は前日を返す」と明示して防いでいる。
起動文を書き換えるときは、この一節を消さないこと。

## よくある操作

### プロンプトを改訂したい

1. `game_ai_prompt.md` の「## 現行版」コードブロックを編集する
2. 冒頭の「現行バージョン」「最終更新」を更新する
3. 「## 変更履歴」に行を追加する（変更点と理由を書く）
4. `main` に反映する

Routine 側の編集は不要。次回の実行から新しい内容が使われる。

### 実行時刻を変えたい / 停止したい / 再開したい

Routine の設定変更で行う。JST から UTC への変換を忘れないこと。

| やりたいこと | 内容 |
|---|---|
| 時刻変更 | `cron_expression` を差し替える。Trigger ID は維持され実行履歴も残る |
| 一時停止 | `enabled` を `false` にする。設定は残る |
| 完全削除 | Trigger を削除する |
| 今すぐ試したい | Trigger を手動発火させる（スケジュール外で1回だけ実行） |

Claude に「論文レコメンドのRoutineを◯時に変更して」と頼めばよい。
claude.ai の Routines 画面からも同じ操作ができる。

### 対象プロジェクトの実装が変わった

`game_ai_prompt.md` の【対象プロジェクトの構成】を更新する。
ここが適用可能性（即適用可 / 要改変 / 参考のみ / スケール不一致）判定の唯一の基準なので、
古いままだと判定が実態からずれる。「既に実測済みで結論が出ていること」のリストも同様。

### 新しいトラックを追加したい

1. `docs/paper_recommend/<track>_prompt.md` を作る。構成は既存2ファイルに合わせる
   （`## 現行版` で始まる見出し＋コードブロック全文、`## 変更履歴`、`## 実行記録`）
2. 既存の起動文をコピーし、参照先ファイル名・Notion DB 名・曜日・
   「この実行は JST の◯曜朝」の一節を差し替えて Routine を作る
3. 上の「登録済み Routine」表に追記する

**トラック間でプロンプトと Notion DB は絶対に共有しない。**
同一DBに混ぜると Interest の傾向学習とテーマ偏りの検出が機能しなくなる。

## 学習ループ

`Interest`（興味あり / 興味なし）を埋めることが、この仕組みの唯一の学習入力。
次回の実行時に過去エントリの Interest 傾向を読み、「興味なし」が付いた Field / Method /
適用可能性 の傾向を避けるようになっている。

登録直後は全件 `保留` で入る。**週に一度、目視で 興味あり / 興味なし に振り分ける**こと。
これを放置すると選定精度が初期状態から改善しない。

## 制約と注意点

### Notion コネクタ

Routine が起動するセッションで Notion の MCP ツールが使えることが前提。
使えない場合、探索とチャット出力までは動くが **Notion 登録（出力2）が丸ごと落ちる**。

これらの Routine は API（MCP 経由）で作成しており、**組織設定により `connectors` パラメータが
利用できず、Notion コネクタを紐づけられていない**。作成時に毎回この警告が返る:

> this trigger stores no MCP connectors, so the sessions it fires will run without
> connector (mcp__<server>__*) tools.

実際、Trigger に保存された `allowed_tools` は組み込みツール（Bash / Read / Write /
WebSearch / WebFetch 等）のみで、`mcp__` で始まるものは1つも含まれていない。

**したがって、各 Routine の初回実行後に Notion DB へ行が増えたかを必ず確認すること。**
増えていない場合の対処は、claude.ai の Routines 画面から **Notion コネクタを有効にした状態で
Routine を作り直す**のが最短（起動文は既存のものをそのまま貼ればよい。作り直したら
API 側の Trigger は削除して二重実行を防ぐ）。

次善策として、`.mcp.json` をリポジトリにコミットし Notion の内部インテグレーション
トークンを環境変数で渡す方法もあるが、ホスト型 Notion MCP が Bearer トークンを
受け付けるかは未検証。OAuth 認証は無人セッションでは完了できない。

### 探索は非網羅的

arXiv には日付別の全件列挙手段がない（`/list/*/recent` は古いキャッシュを返し、
`export.arxiv.org/api/query` は robots.txt でブロックされる）。
このワークフローはキーワード検索に依存しており、取りこぼしは原理的に発生する。
仕様書側で「5テーマ × 各2回以上、合計10回以上の検索」を課してこれを緩和している。

### 実行記録

各実行の末尾で `<track>_prompt.md` の「## 実行記録」表に1行追記して push する。
プロンプト定義ファイルが `main` にある場合は `main` へ、
まだブランチ上にしかない場合はそのブランチへ commit する。
コミットメッセージには `[skip ci]` が付く。

数回分たまったら、密度の見積もり（週2〜4件）と下限2件の妥当性を見直すこと。
現状の見積もりは 2026-07-29 のサンプル1回のみに基づいている。
